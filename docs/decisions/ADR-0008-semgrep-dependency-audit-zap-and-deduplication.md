# ADR-0008: Semgrep, offline dependency audit, OWASP ZAP and cross-scanner de-duplication (Stage 10 completion)

Status: Accepted by the owner's instruction to finish Stage 10 (2026-10-23); decisions below were taken within it and are recorded for review. Extends ADR-0007 (which built Bandit only). Resolves Q73-Q75 and Q79 in the form described here, with the verification gaps listed under "What was and was not verified". Opens Q81-Q86.

## Context
ADR-0007 deliberately left Semgrep, the dependency audit and ZAP unbuilt because the sandbox is offline and pure-Python. The owner now asks for all three plus de-duplication across scanners. The development environment for this change had **no outbound network**, no Semgrep, no ZAP image, no `pip-audit` and no advisory database, and could not install any of them. Every decision below is therefore shaped by one rule: build the integration, keep it safe, and never claim a third-party tool works until it has run.

## Decisions

### Shared
1. **One fixed command table, one image per kind.** `execution/commands.py` gains `semgrep_static`, `dependency_audit`, `zap_baseline`, `zap_active`. `CheckCommand.image` selects the image: `base` (`SANDBOX_IMAGE`: pytest, Bandit, dependency audit), `scanner` (`SANDBOX_SCANNER_IMAGE`: base plus Semgrep), `zap` (`SANDBOX_ZAP_IMAGE`). Nothing from a request reaches a Docker argument except the ZAP URL, which is rebuilt from validated parts (decision 12).
2. **A common parsed-report shape** (`execution/scan_report.ParsedScan`) and shared defensive helpers (`execution/report_common`). Bandit keeps its own module and now imports the shared helpers; behaviour is unchanged (its tests pass untouched).
3. **Same status rule as Bandit** (ADR-0007 #4): `passed` only for a valid report with no findings and no tool problems; a missing/invalid report, an unexpected exit code, or a tool that reported problems with no findings is `error`; timeouts/OOM/cancel never produce a scan. Findings are created `new` + `unverified`; only a person confirms.
4. **Normalization.** Every scanner yields `FindingResult` with the same fields: tool, rule id, title, severity (info..critical), confidence (kept apart from severity), category (`static_analysis` | `dependency` | `dynamic`), path/line (line optional), component, CWE, aliases, fingerprint, limitations. Migration 0008 adds `cwe`, `component`, `aliases`, `group_id`.

### Semgrep (CLI, local rules, offline)
5. Semgrep is a compiled tool, so it lives in a **separate image** (`sandbox/Dockerfile.semgrep`, `make scanner-image SEMGREP_VERSION=...`) built by the operator with network access. At run time the container has no network. The command is fixed: `semgrep scan --config /opt/sentinel/semgrep-rules --metrics=off --disable-version-check --json --output /tmp/semgrep.json ...` with **local rules only** (no registry, no login). The starter rule bundle (`sandbox/semgrep-rules/*.yml`: 10 Python + 6 JS/TS rules) is authored in this repository; more can be added after `semgrep --validate`.
6. The report is untrusted: Semgrep's `extra.lines` (matched source) is dropped, rule ids lose the rules-directory prefix, severity comes from the rule, confidence from rule metadata (`low` if absent), CWE from rule metadata. Any reported error makes the scan incomplete (it can never verify a fix).

### Dependency audit (offline advisory bundle; no pip-audit)
7. **Why not pip-audit/osv-scanner:** both need an advisory feed at run time (network), which the sandbox must not have, and neither could be installed or evaluated here. Instead the audit is a small stdlib-only script (`sandbox/dep_audit.py`) that reads lockfiles **as data** and matches locked versions against an **advisory bundle baked into the image**.
8. **Advisory data strategy.** `sandbox/advisories.py` (operator step, needs network, `make advisories`) downloads the OSV PyPI and npm dumps (which republish the GitHub Advisory Database and PyPA advisories), compacts them (id, aliases, clipped summary, severity, CWE, affected ranges, fixed versions) into `sandbox/advisories/{pypi,npm}.json` plus `meta.json`, and `make sandbox-image` bakes them in and sets the image label `sentinel.advisories.fetched_at`. **The host reads that label, not anything the container says**, and `blocked`s the check if it is missing or older than `DEPENDENCY_ADVISORY_MAX_AGE_DAYS` (default 30): stale data would turn "no known issues" into a false all-clear. Licence terms of the OSV feeds must be checked by the operator before shipping an image (Q82).
9. **Supported lockfiles:** `poetry.lock`, pinned `requirements*.txt`, `Pipfile.lock` (PyPI); `package-lock.json`/`npm-shrinkwrap.json` (npm). `yarn.lock`, `pnpm-lock.yaml`, `Cargo.lock`, etc. are detected and reported as unsupported, which makes the scan **incomplete** (no auto-verification) and, with no findings, an `error` rather than a pass. Matching follows OSV range semantics (PEP 440 via the vendored `packaging`; a small SemVer comparator for npm); a version that cannot be compared is reported, never guessed. One finding per (ecosystem, package, version, advisory) regardless of how many lockfiles pin it.
10. **Honest limits:** confidence `high` means only "this exact version is in the affected range"; reachability is not assessed; unpinned/unlocked dependencies and transitive packages absent from the lockfile are not covered; data is as old as the bundle.

### OWASP ZAP (Docker, authorized targets only)
11. **Gates, all before any container exists** (`DockerSandboxExecutor._prepare_zap`), on top of the existing plan-time, submit-time and worker-time authorization gate: ZAP image + network configured **and** `SANDBOX_ZAP_EGRESS_ATTESTED=true`; a target exists; its environment is `development`/`staging` (never production, never localhost: a network-less sandbox cannot reach loopback anyway); the URL is rebuilt as `origin + validated url_path` (no query, fragment, credentials or option-like text); the host is a public DNS name (no IP literals, no internal-looking names); the **worker resolves the host itself** and every address must be global.
12. **Network restriction (defence in depth, in this order of strength):** (a) the container joins only the operator-provisioned network named by `SANDBOX_ZAP_NETWORK` (never `host`/`bridge`/`none`), which the operator must restrict at the host firewall (DOCKER-USER chain) to the scan targets; Sentinel cannot verify those rules, so it requires an explicit attestation setting; (b) the target host is pinned with `--add-host host:ip` to the address the worker verified; (c) DNS is pointed at a black-hole address (192.0.2.1), so no other name resolves, redirects to other hostnames fail, and DNS cannot be used to exfiltrate; (d) the parser drops any alert instance whose host is not the authorized host and records the fact; (e) everything else about the container is unchanged: read-only rootfs, all capabilities dropped, no-new-privileges, uid 65534, tmpfs only, pids/memory/CPU/time limits, no mounts/devices/socket/env, labelled and removed in `finally`.
13. **Scan profiles.** `zap_baseline` runs `zap-baseline.py` (spider ~1 min, passive rules; risk medium; needs target authorization). `zap_active` runs `zap-full-scan.py` (active attack-style requests); it keeps `always_requires_approval`, `high` risk and the existing rule that the authorization must allow mutating methods. No scan profile, script, config file or ZAP option is accepted from a plan or request; unknown parameters are refused.
14. **Report handling:** ZAP's `evidence`, `attack`, `otherinfo` and any request/response data are dropped (they quote the target's responses); query strings and fragments are stripped from URLs; descriptions are stripped of markup and clipped. ZAP findings are **always incomplete scans**: a crawl cannot prove an alert is gone, so ZAP findings are never auto-verified as fixed.
15. **ZAP is disabled by default** and stays unable to run until an operator builds `sandbox/Dockerfile.zap`, provisions and attests the network, and completes the verification checklist in the threat model. This is a deliberate consequence of decision 12(a).

### De-duplication
16. **Findings are never merged.** `finding_groups` (+ `findings.group_id`) links findings that describe one issue; each keeps its own tool, rule, evidence link(s), status and verification state, so the original scanner output is preserved and a person can still triage them separately. Groups are derived data, recomputed (`services/dedup.py`) after every scan and never change a status.
17. **Rules, deliberately conservative:** `location` = same source and file, same CWE, lines within 3 of a neighbour, **at least two different tools**; `advisory` = same component (`pypi:name@ver`) sharing an advisory alias (a GHSA and a PYSEC that both name one CVE). Dynamic findings are not grouped with static ones (a URL is not a source line). Group keys are derived from the smallest member fingerprint, so they do not churn as members come and go.
18. **API/UI:** `GET /projects/{id}/finding-groups`; findings carry `cwe`, `component`, `aliases`, `group_id`; finding detail lists `related` members. The findings panel shows the reporting tool, a "Linked duplicate" badge and the related findings.

## Update 2026-10-23 (owner follow-up actions run)
- **Dependency audit now verified with REAL data.** `make advisories` ran (PyPI 31,031 and npm 232,804 advisories, fetched 2026-10-23); `make sandbox-image` baked them in and set the label. A real run in the locked-down container matched Django 2.2.0 against dozens of real advisories (for example CVE-2022-28346, CVE-2019-14234, with PYSEC/GHSA/BIT aliases) and lodash 4.17.20 (CVE-2021-23337), and left current versions unmatched. Licence review (Q82) is still open.
- **Semgrep now verified.** Scanner image built with `semgrep==1.182.1` (`make scanner-image ... DOCKER_BUILD_ARGS=--network=host`, because Docker's default bridge had no internet; build-time only). The executor's fixed command ran offline (`--network none`) on a deliberately vulnerable project: 16 of 16 bundled rules loaded and fired with correct lines, CWE and severity; a literal `eval('1+1')` was correctly not flagged. `semgrep --validate` is NOT usable offline (it fetches lint rules from semgrep.dev); the working validation is a scan.
- **ZAP: container mechanics verified in a lab; the security preconditions are NOT, so it stays disabled.** The official image (`ghcr.io/zaproxy/zaproxy:stable`, ZAP 2.17.0, digest sha256:5ccfff9a...) was pulled and `sandbox/Dockerfile.zap` built. The lab ran `zap-baseline.py` through the SAME `create_argv` hardening (read-only root, all caps dropped, no-new-privileges, uid 65534, noexec tmpfs, 2 GiB, 512 pids, black-hole DNS, pinned `--add-host`) on an `--internal` Docker network (no internet, no host route) against a disposable local target: exit 0 in 44 s, a framed report, parsed by `zap_report.py` into 15 real alerts, all scoped to the target host. The lab found and fixed three real defects in my unverified Dockerfile: (1) `/zap/wrk` linked to `/tmp` made ZAP's own `zap.yaml` copy fail, so it now links to the `/workspace` tmpfs and the ZAP result file is `/workspace/zap.json`; (2) Java takes its home from the passwd entry (`/nonexistent`), not `$HOME`, so the image passes `-Duser.home=/tmp` through `SENTINEL_JAVA_TOOL_OPTIONS`; (3) a network-less JVM cannot resolve its own hostname (irrelevant with a network, noted for lab use). **Still NOT verified:** the host-firewall restriction (needs root on the operator's host); the production path against a public name (real DNS resolution and pinning end to end, the executor `_prepare_zap` flow with a real runner); `zap_active`; behaviour on a real remote target; SANDBOX_ZAP_NETWORK semantics on a non-internal network. ZAP stays disabled: `SANDBOX_ZAP_IMAGE`/`SANDBOX_ZAP_NETWORK` are unset and `SANDBOX_ZAP_EGRESS_ATTESTED` is false.
- Real database: already at 0007; 0008 applied after reviewing the generated SQL (additive only).

## What was and was not verified (the honest part) - as of the original Stage 10 completion, superseded above where noted
- **Verified by running:** all parsers against fixtures in the tools' documented formats; command and spec construction; executor gating and status mapping with a fake runner; migration 0008 up/down and the DB paths (ingestion, grouping, API) on a disposable PostgreSQL; **the dependency audit end to end in a real locked-down container** (built locally from the existing base image) against a **synthetic** advisory bundle with fake ids, proving lockfile parsing, range matching, framing, host-side parsing, the label-based age check and the container's `--network none`, read-only root and dropped capabilities.
- **NOT verified:** Semgrep (not installable here: the scanner image was never built, the flags and JSON shape follow its public documentation, the bundled rules were never run through `semgrep --validate`, and the executor's result against a missing scanner image is `failed_to_start`, which was observed); OWASP ZAP (no image, no network, the ZAP Dockerfile, script paths and `-J` report location are unverified, no attacked or even reached target); the real advisory download (`advisories.py` was never run against OSV; its record-compaction logic is unit-tested with fixtures); real advisory data (only synthetic); the firewall restriction behind `SANDBOX_ZAP_NETWORK`; gVisor/Kata.
- Consequently **no claim is made that Semgrep or ZAP works.** They are integrated, gated and tested up to the process boundary.

## Consequences
- Two more images to build and keep current (scanner, ZAP) and a periodic `make advisories` run; the dependency audit refuses stale data by design.
- The ZAP network guarantee rests on an operator-owned firewall rule plus an attestation flag; a misattested network is an operator error Sentinel cannot detect (Q83).
- A new migration (0008) and one new endpoint.
- The dependency audit needs a lockfile; projects with only unpinned manifests are `deferred` at planning time (unchanged).
