# ADR-0007: Security scanning and finding verification (Stage 10)

Status: Accepted (owner go-ahead for Stage 10 on 2026-10-24; owner approved adding Bandit through Poetry). Decisions below were taken within that approval and are recorded for review. Narrows Q36 and Q69; opens Q73-Q80.

## Context
Stage 10 asks for security tool integrations, normalized and de-duplicated findings, finding states and verification attempts, and approval gates for intrusive checks. The findings tables (`findings`, `finding_events`, `finding_evidence`, `verification_attempts`) already existed from migration 0002; no scanner wrote to them and no API read them. The sandbox is offline (ADR-0005/0006), so a scanner must be pure Python, vendorable from `poetry.lock`, and must not execute the project.

## Decisions
1. **Bandit is the one scanner built in this stage.** It is pure Python (AST analysis of source text, nothing imported or executed), so it runs in the existing offline sandbox. `bandit` is a backend dev dependency (pinned by `poetry.lock`) and is vendored with its pure-Python dependencies (stevedore, PyYAML without its C accelerator, rich, markdown-it-py, mdurl) by `sandbox/vendor.py`. Bandit's dist-info `entry_points.txt` is kept so its plugins are found offline.
2. **Semgrep, dependency audit and OWASP ZAP are NOT built.** Semgrep ships a compiled binary and fetches rules over the network; a dependency audit needs an advisory feed (outbound network); ZAP needs a reachable, authorized target and a ZAP image. None has a runner (`commands.lookup` returns `None`), so each is recorded `skipped` ("no sandbox runner") and can never report a result. The catalog's gates stay as they were: `zap_active` and `load_basic` always need approval, remote targets pass the target gate, production stays blocked. This resolves the "approval gates for intrusive checks" item by keeping those checks unable to run, not by building a ZAP runner (Q73-Q75).
3. **`bandit_static` is a fixed command**: `python -P -m bandit -r . -f json -o /tmp/bandit.json -q -x ./.git,./node_modules,./.venv,./venv`. `-P` keeps the project's directory off `sys.path`, so a project file named `yaml.py`, `bandit.py` or `stevedore.py` is never imported (tested). No plan parameter is accepted except `timeout_seconds`. It is not a "project code" check, so it does not need `SANDBOX_ALLOW_PROJECT_CODE`.
4. **Result status comes from the exit state and a valid report.** Exit 0/1 with a valid report: no findings and no unreadable files is `passed`; findings is `failed` ("N issues; each is unverified"); unreadable files and no findings is `error`. A missing or invalid report, any other exit code, OOM, timeout or cancel never yields `passed` and never produces a scan.
5. **The report is untrusted data.** It is parsed by `execution/bandit_report.py` only (size-capped by the framing layer, type-checked fields, control characters stripped, text clipped, rule ids matched against `B\d{3}`, paths accepted only if plain relative). Bandit's `code` snippet is dropped: it can contain the secret a rule flagged. The stored `bandit.json` evidence is re-serialized from validated fields only. Messages of B105/B106/B107 have the quoted value replaced with `'<redacted>'`.
6. **Findings are created `new` + `unverified`, with the tool's own confidence stored separately from severity.** A scanner never sets `likely` or `confirmed`. Every finding links (`finding_evidence`) to the stored scan report that produced or re-reported it, and carries a plain-text `limitations` ("static pattern match; exploitability not established; a clean result does not mean the code is secure").
7. **Normalization and de-duplication.** Fingerprint = `bandit:` + sha256 of (tool, rule id, file, normalized message, occurrence index within the file). It survives line moves; two identical issues in one file stay distinct. `(project_id, fingerprint)` is unique, so a repeat updates the row (`occurrences`, `last_run_id`, current line) and adds a `seen_again` event instead of a duplicate.
8. **Finding states.** People may set `triaged`, `in_progress`, `fixed`, `false_positive`, `accepted_risk` (and `reopened` from a resolved state) along an explicit transition map; `false_positive` and `accepted_risk` need a note and the administrator-level risk-decision permission (matches the documented matrix); developers cannot. `verified_fixed` and automatic `reopened` come only from scans. Changing anything needs project `run` access (a read-only break-glass grant cannot) and every change and refusal is audited.
9. **Verification attempts.** A later *complete* scan (valid report, no unreadable files, not truncated) of the same source that no longer reports a finding records a `rescan` attempt: `new/triaged/in_progress/reopened -> fixed`, and `fixed -> verified_fixed` on a second such scan. Reported again after `fixed`/`verified_fixed` -> `reopened`. An incomplete or failed scan never counts as "gone". A person's `false_positive`/`accepted_risk` decision is never changed by a scan. People can record `likely`, `confirmed`, `not_reproduced` or `inconclusive` with a note (at least 10 characters); `confirmed` is refused (409, audited) without an evidence row, and the database refuses it too.
10. **API.** `GET /projects/{id}/findings`, `GET /findings/{id}` (events, evidence, attempts), `POST /findings/{id}/status`, `POST /findings/{id}/verification`. No endpoint creates, edits the text of, or deletes a finding. The design doc's `PATCH /findings/{id}`, manual evidence attach and `verify-fix` run endpoints are not built (Q77).
11. **Migration 0007** adds `confidence`, `rule_id`, `file_path`, `line_number`, `source_id`, `limitations`, `occurrences` to `findings`, and `method` + `evidence_artifact_id` to `verification_attempts`, and extends the `finding_events.event_type` check. All additive.

## Consequences
- Only Python source gets static analysis. A clean Bandit result says nothing about other languages, logic flaws, dependencies or the running application.
- Bandit is a heuristic matcher: expect false positives (that is why states and `false_positive` exist) and false negatives.
- Re-scan verification is per source: a re-uploaded archive is a new source, so findings from the old source are not auto-verified by it (Q78).
- The image must be rebuilt (`make sandbox-image`) to include Bandit.
