# Sandbox Threat Model (Stage 8)

> Status: **implemented and tested in Stage 8** (ADR-0005). Scope: the Docker sandbox that executes fixed catalog commands for approved runs. Read with `JOB_AND_SANDBOX_DESIGN.md`, `SECURITY_AND_SAFETY.md`.

## What is protected, from whom
**Assets:** the host and its other containers, platform secrets (DB, Redis, session pepper, API keys), the artifact store and other projects' data, the Docker daemon, and result integrity.
**Trusted:** the API, the worker, PostgreSQL, Redis, the Docker daemon, the fixed runner script in the image (`sandbox/entry.py`, `smoke.py`).
**Untrusted:** uploaded ZIP bytes and names, any code inside them, everything a sandbox prints, every file it creates, and its timing.
**Attacker goals:** escape to the host, read secrets or other projects, reach the network (SSRF, exfiltration), exhaust resources, forge results, persist after cancel/timeout, or poison logs.

## Threats and controls
| # | Threat | Control (enforced in code) | Test |
|---|---|---|---|
| T1 | A compromised worker controls Docker (the `docker` group is root-equivalent) | The worker never runs untrusted code. `DockerRunner` runs fixed argv vectors (no shell); container names are generated, labels are UUIDs/validated values, the image/runtime/scope are regex-validated in settings and again in `SandboxSpec.validate`. No request field reaches a Docker flag. The CLI gets a minimal environment (no worker secrets). **Residual risk, see below.** | `test_sandbox.py` (argv, validation) |
| T2 | Container escape (kernel/runc bug) | No `--privileged`, devices, host mounts or Docker socket; `--cap-drop ALL`; `no-new-privileges`; default seccomp and AppArmor; read-only rootfs; non-root numeric user `65534:65534`; `--ipc none`; own PID/mount/UTS namespaces; `--init`. `SANDBOX_RUNTIME` selects a stronger runtime (gVisor `runsc`, Kata) without code changes. | `test_sandbox_docker.py` (identity/caps, configuration as the daemon sees it, filesystem) |
| T3 | Reading platform secrets or host files | Empty container environment (fixed `PATH/HOME/LANG` only); no bind mounts or volumes; the source ZIP is streamed over stdin, never mounted; `/workspace` and `/tmp` are fresh per-container tmpfs. | env, mounts and host-path tests |
| T4 | Network use (SSRF, exfiltration, cloud metadata, host loopback) | `--network none`, unconditionally; no setting enables it. Only `lo` exists in the container. Checks that need a network target return `blocked` before any container exists. | network test (loopback host port, bridge gateway, internet, metadata, DNS, interfaces) |
| T5 | Resource exhaustion | `--cpus`, `--memory` with `--memory-swap` equal (no swap), `--pids-limit`, `nofile`, `fsize`, `core=0` ulimits, size-capped tmpfs (which count against memory), output cap in the host reader (surplus is drained and discarded), timeout in the runner **and** a host deadline (timeout + 5 s) that kills a container whose runner was frozen. `nproc` is deliberately not used (it is per-uid host-wide, not per container). | memory, pids, disk, flood, timeout, frozen-runner tests |
| T6 | Malicious ZIP (traversal, absolute, symlink/device, duplicate, bomb, huge count) | Header validation again on the host (`archive.inspect_archive`, nothing extracted on the host). Extraction happens only inside the sandbox: strict name checks, no special files, `O_EXCL|O_NOFOLLOW`, real byte counts (not header claims), file/total/count caps, `0600` files. | extractor unit tests, six hostile-archive container tests |
| T7 | Another project's workspace or tampered upload | The worker resolves the source only from the run's own project (`projects.list_sources(project_id)` and `get_artifact(project_id, ...)`), the executor re-reads the bytes once, checks SHA-256 against the recorded value, and sends exactly those bytes. Storage keys are validated against the store root. | workspace-scope, hash-mismatch tests |
| T8 | Forged or poisoned output | The host takes status only from `docker inspect` (exit code, `OOMKilled`) and its own timers, never from output. Output is decoded safely, stripped of control/ANSI sequences, redacted of configured secrets and credential shapes, capped, and stored under fixed names with SHA-256. | forge, redaction, evidence e2e tests |
| T9 | Containers outliving a cancel, timeout or lost worker | `always rm -f -v` in `finally`; `terminate(batch)` removes by label and verifies; the reconciler calls it for lost, overrunning and unconfirmed-cancel batches; a janitor sweep removes this scope's labelled containers past `test timeout + grace + 120 s`; the runner has its own timeout. All cleanup filters on `sentinel.sandbox=1` **and** the deployment scope label, so other containers are never touched. | cancel, cleanup, janitor, reconciler e2e tests |
| T10 | Unauthorized or risky targets | Stage 7 revalidation is unchanged. Only commands from the fixed table run; unknown checks are `skipped`; network checks `blocked`. `JOB_EXECUTOR=stub` is the default; `docker` is an operator opt-in. | unit and e2e tests |

## Stage 9 additions: running a project's own tests (ADR-0006)
Stage 8 executed only our fixed script. Stage 9 executes the project's pytest suite, so everything the project can do from inside a test is now in scope. The container recipe is unchanged and was re-verified **from inside real pytest runs** (`test_sandbox_pytest.py`).

| # | Threat | Control | Test |
|---|---|---|---|
| T11 | Project code is deliberately hostile (escape, secrets, network, host files) | Same recipe as T2-T4. Project code is off by default (`SANDBOX_ALLOW_PROJECT_CODE=false`); enabling needs `JOB_EXECUTOR=docker` plus a stronger `SANDBOX_RUNTIME` or an explicit `SANDBOX_ACCEPT_SHARED_KERNEL=true`; otherwise `blocked`, no container. | project tests assert no env secrets, no network (host loopback, gateway, internet), no Docker socket, read-only root and vendored code, uid 65534, zero capabilities, non-executable tmpfs |
| T12 | The project forges or sabotages the result file (XML bomb, DOCTYPE/ENTITY, 3 MiB file, symlink to `/etc/passwd`, FIFO, garbage, fake frames, lying "all passed" report) | The in-image runner frames only a regular, non-symlink file of at most 2 MiB; the host verifies nonce, length and hash, takes the last valid frame, rejects DOCTYPE/ENTITY, caps size and case count, strips control characters, clips text. A bad report yields no cases and no `junit.xml`, never a crash. **Status comes from the exit code**, so a forged report cannot turn a failing run into a pass. | `test_hostile_result_files_*` (5 cases), `test_a_forged_report_*`, unit frame/JUnit tests |
| T13 | Output flood hides the result or fills the host | Host reader caps stored output and discards the rest; the tail ring buffer keeps the frame reachable. | `test_output_flood_does_not_hide_the_result` |
| T14 | Resource abuse by tests (infinite loop, memory hog, fork bomb) | Existing limits; per-test `timeout_seconds` can only shorten the limit; OOM is `error`, timeout `timed_out`; a timed-out test does not stop later tests. | loop, memory, fork-bomb, cancel tests |
| T15 | Option/path injection through plan parameters (`-p evil`, `--rootdir=/`, `../..`) | `target_path` regex plus no leading `-`, no `..`; unknown parameters rejected; passed after `--`; validated at plan time and again in the executor. | 16 parameter cases |
| T16 | Reading evidence you should not see, or tampered evidence | Project grant only (break-glass read-only, audited); only run evidence kinds; stored hash re-checked; DB refuses traversal storage keys; attachment, `nosniff`, `no-store`, CSP; UI renders text only. | `test_results_and_evidence_follow_the_project_grant`, `test_only_run_evidence_is_served_and_tampering_is_detected`, frontend test |
| T17 | A project file named like one of the scanner's own imports (`yaml.py`, `bandit.py`, `stevedore/`) is loaded when the scanner starts, running project code in a check that is meant to run none | The command is `python -P -m bandit ...`: the working directory is never put on `sys.path`; Bandit only parses source text. Not a "project code" check, so it does not need the opt-in; this test proves why that is safe. | `test_clean_unreadable_and_hostile_projects` (shadow files print a marker that never appears in any evidence), `test_bandit_command_is_fixed_offline...` |
| T18 | A scan report that lies, floods or smuggles content (forged frame, huge or malformed JSON, traversal paths, control characters, rule ids that are not rule ids) | Same nonce/sha256 frame as T10-T12; JSON-only parse with type checks; findings capped at 2000; paths must be plain relative; rule ids must match `B\d{3}`; text clipped and stripped; only validated fields are stored. | 20+ cases in `test_bandit_scanner.py` |
| T19 | The scanner quotes a secret from the project (hardcoded password rules) into findings or evidence | Bandit's `code` snippets are never stored; the stored `bandit.json` is re-serialized from validated fields; B105/B106/B107 messages have the quoted value replaced; known platform secrets are also redacted. | `test_findings_are_normalized_and_never_carry_code_or_the_flagged_secret`, `test_a_real_bandit_scan_produces_unverified_findings_with_evidence` |
| T20 | A scan that did not finish is read as "all clear", or marks old findings fixed | `passed` needs exit 0/1 *and* a valid report; a missing or invalid report, other exit codes, OOM, timeout or cancel give `error`/infrastructure states and no scan. Re-scan verification needs a complete scan (no unreadable files, not truncated) of the same source. | `test_a_clean_pass_needs_a_valid_report`, `test_infrastructure_states_are_never_scan_results`, `test_rescan_verification_needs_a_complete_scan...` |
| T21 | A scanner's output (or a model's) is treated as confirmed, or a read-only grant changes a finding | Scans create `unverified` findings only; `confirmed` needs a person, a note and evidence (service check plus DB trigger); `false_positive`/`accepted_risk` need administrator permission and a note; changes need project `run` access so read-only break-glass is refused; every change and refusal is audited. | `test_review_states_and_verification_follow_the_rules`, `test_break_glass_can_read_findings_but_not_change_them` |

What a hostile project **can** still do: lie about its own cases, make its own tests pass, consume its own limits, and (under plain runc) attempt a kernel exploit. It cannot change another project's data, the platform, or the status derived from crash/timeout/OOM/cancel.

## Stage 10 additions: Semgrep, offline dependency audit, OWASP ZAP (ADR-0008)
Semgrep and the dependency audit run in the same locked-down recipe as Bandit (no network, read-only root, no capabilities, uid 65534, tmpfs only). They read the project as data and execute none of it. **ZAP is the first and only container that may have a network**, so it gets its own controls. Rows marked *fixture* were verified only against fixtures or a fake runner; rows marked *container* were verified in a real container; rows marked *NOT RUN* depend on a tool or network that was unavailable.

| # | Threat | Control | Verified |
|---|---|---|---|
| T22 | A scanner sends the project or its secrets out (Semgrep metrics/registry/version check, an advisory lookup) | Containers keep `--network none`; Semgrep runs with local rules, `--metrics=off`, `--disable-version-check` and `SEMGREP_SEND_METRICS=off`; the audit reads a baked-in bundle, never a feed | argv assertions (*fixture*); audit in a no-network container (*container*); Semgrep *NOT RUN* |
| T23 | A rules/advisory bundle is poisoned or stale (a stale bundle gives a false "no known issues") | Bundles are built by an operator step into the image; the **image label** (not the container) carries the fetch time; the host `blocked`s the audit when it is missing or older than `DEPENDENCY_ADVISORY_MAX_AGE_DAYS`; sizes and fields are clipped | age check with a fake runner (*fixture*) and the real label read (*container*) |
| T24 | A lockfile or Semgrep/ZAP report is hostile (huge, malformed, traversal paths, control characters, ids that are not ids, markup) | Lockfiles parsed as data with size/count/depth caps and per-file errors; reports framed with a nonce and hash, parsed with `json` only, type-checked, clipped, rule/package/advisory ids matched against strict patterns, paths accepted only if plain relative, HTML stripped | parser tests (*fixture*) |
| T25 | Scanner output quotes secrets (Semgrep matched lines, ZAP evidence/attack/response data, URL query tokens) | Semgrep `extra.lines` and ZAP `evidence`/`attack`/`otherinfo` are never kept; query strings and fragments are stripped; stored `*.json` evidence is re-serialized from validated fields and redacted | tests assert the secrets are absent (*fixture*) |
| T26 | ZAP is pointed at an unauthorized, internal, production or hostile target | Plan-time, submit-time and worker-time target authorization (existing). Then, before a container exists: ZAP enabled + attested; target present; environment development/staging; URL rebuilt from origin + validated path; host must be a public DNS name (no IP literals, no internal-looking names); the **worker resolves the name and every address must be global** (blocks 10/8, 127/8, 169.254/16 including cloud metadata, ULA, loopback, multicast) | gating matrix with a fake runner (*fixture*) |
| T27 | ZAP reaches a host other than the target (redirects, links, DNS rebinding, DNS exfiltration, metadata service) | (1) only the operator-provisioned network `SANDBOX_ZAP_NETWORK` (never host/bridge/none), restricted at the host firewall to scan targets; (2) the target name is pinned with `--add-host name:ip` to the verified address; (3) DNS is a black hole (192.0.2.1), so no other name resolves; (4) the parser drops alert instances whose host differs and records it. **(1) is the operator's responsibility**: Sentinel cannot see the firewall, so ZAP refuses to run without `SANDBOX_ZAP_EGRESS_ATTESTED=true` | spec/argv assertions and parser scope test (*fixture*); the firewall *NOT RUN* |
| T28 | Plan parameters smuggle ZAP/Semgrep options (`-z`, scan policy, config path, `--config p/ci`) | Only `timeout_seconds` (and `url_path` for ZAP) are accepted; unknown parameters are refused; ZAP's script, flags and report path are fixed; the URL has no query or `-` prefix | tests (*fixture*) |
| T29 | An intrusive scan runs without approval or against more than was authorized | `zap_active` keeps `always_requires_approval`, high risk, and the authorization must allow mutating methods; baseline needs a target authorization; the per-run time limits cap duration | existing policy tests + catalog test (*fixture*) |
| T30 | A dynamic scan "proves" a fix, or a scanner finding is read as confirmed | ZAP scans are always incomplete (never auto-verify); all findings are created `unverified`; a failed/partial scan never counts as clean; the status comes from the exit state plus a valid report | unit + DB tests |
| T31 | De-duplication hides a real finding or loses evidence | Groups only link; no finding is merged, hidden, re-statused or deleted; each keeps its tool, rule, evidence and state; location groups need two different tools, same file and CWE, nearby lines | DB tests (*container-less DB*) |

### ZAP network (operator checklist: do this before setting `SANDBOX_ZAP_EGRESS_ATTESTED=true`)
1. Create a dedicated user-defined bridge network (`docker network create sentinel-zap`), used by nothing else.
2. In the host firewall's `DOCKER-USER` chain, allow traffic from that network's subnet only to the addresses/ports of the scan targets you have authorized (and DROP everything else, including RFC 1918 ranges, link-local and the cloud metadata address 169.254.169.254, and the host's own addresses). Verify with a test container: a request to an unlisted public IP, to the host's docker0 gateway and to 169.254.169.254 must all fail.
3. Build `sandbox/Dockerfile.zap` from a ZAP image you have reviewed and pinned (`make zap-image ZAP_BASE=...`).
4. **ZAP verification (container mechanics done 2026-10-23 on an `--internal` lab network with ZAP 2.17.0: starts as uid 65534 on a read-only rootfs, JVM runs under noexec tmpfs and the memory limit, `/workspace/zap.json` is framed and parses; firewall, public-target and active-scan checks are NOT done):** run `zap-baseline.py` once against a local, disposable test site on the restricted network and confirm: the container starts as uid 65534 on a read-only rootfs with the tmpfs sizes in `config.py`; `/workspace/zap.json` is produced and framed; the JVM works with `noexec` tmpfs and the memory limit; the report matches `execution/zap_report.py`. Fix the Dockerfile or parser if not.
5. Set `SANDBOX_ZAP_IMAGE`, `SANDBOX_ZAP_NETWORK`, `SANDBOX_ZAP_EGRESS_ATTESTED=true`.

## Residual risks (accepted for Stage 8, tracked in OPEN_QUESTIONS)
1. **Docker group = root on the worker host (Q58).** A bug in worker code that lets an attacker influence Docker arguments would be host compromise. Mitigated by fixed argv and validation, not eliminated. Run workers on a dedicated host/VM; prefer rootless Docker or a socket proxy later.
2. **Shared-kernel isolation (Q59).** Hardened runc is the baseline. Stage 8 executed only our own fixed script; **Stage 9 runs the project's own pytest suite**, so for genuinely untrusted projects in production use gVisor/Kata or disposable VMs (`SANDBOX_RUNTIME`), or accept the shared-kernel risk explicitly with `SANDBOX_ACCEPT_SHARED_KERNEL=true`. Project code is off unless one of these is chosen.
3. **No egress, therefore no dependency installation (Q60/Q66).** The dependency audit now runs offline against a baked-in advisory bundle (Stage 10, ADR-0008). Only the standard library and the vendored pytest stack exist in the sandbox; projects importing anything else report `error` with an explanation. Allow-listed egress or a prebuilt wheelhouse needs its own design; localhost-target reach (Q26) stays unsupported (such checks are `blocked`).
4. **Image supply chain (Q61).** The runner image is built locally from `python:3.12-slim` without pulling; pin it by digest and rebuild regularly. The image ID is recorded in each manifest.
5. **tmpfs is `noexec` (Q62).** Fine for Stage 8; Stage 9 runners may need an executable scratch area, to be justified then.
6. **Host-wide capacity (Q63).** Concurrency is bounded by Celery concurrency and `JOB_MAX_CONCURRENT_BATCHES`; there is no host-wide CPU/memory accounting across workers.
7. **Evidence retention (Q70).** Evidence is stored, hashed, authorized and downloadable (Stage 9), but there is no retention sweeper yet.

## Operating notes
- Build once: `make -C backend sandbox-image` (tag `sentinel-sandbox-runner:stage8`). Enable with `JOB_EXECUTOR=docker`; leave `SANDBOX_SCOPE` per deployment (tests use unique scopes).
- Never run the worker as root, never add the worker to a shared host's docker group, never mount the Docker socket into anything the worker starts.
- Verify after changes: `poetry run pytest tests/integration/test_sandbox_docker.py` (needs Docker and the image).
